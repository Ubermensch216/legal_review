# 토큰 한도와 무관하게 끝까지 검토하는 단계형 파이프라인 설계

## 이번 실패의 원인

- S3는 최대 4개 조문 원문을 한 호출에 묶으면서 S1용 공통 접두부(질의, 첨부문서, 전체 근거 색인)를 다시 붙인다. 캐시 이점보다 입력 증가가 커지면 조문 자체는 짧아도 30,208토큰 한도를 넘는다.
- S6는 최대 12개 주장·근거 쌍을 한 호출에 묶고 S4용 실행 접두부를 다시 붙인다. 이번에는 38,051/31,232토큰이었다. 12쌍을 넘는 대상은 현재 확인 없이 남는다.
- 상한은 `runStage`에서 검출하지만, 호출 단위를 다시 쪼개지 않는다. S3의 골격 대체는 의미상 요건 분해 성공이 아니고, S6의 미확인은 최종 결론의 검증을 완료하지 못한 상태다.
- 현재 S6는 임베딩 유사도가 높은 쌍을 `SUPPORTED`로 인정한다. 유사성은 법적 함의를 보증하지 않으므로, 검증 절차를 재설계할 때 이 경로도 바로잡아야 한다.

## 기본 원칙

**한 호출은 한 가지 작은 판단만 한다.** 전체 사건 자료는 ID와 해시를 가진 저장소에 유지한다. 모델에는 그 판단에 필요한 사실, 조문 단위, 주장, 인용 원문의 최소 묶음만 보낸다. 후속 단계에는 원문 대신 구조화된 작은 결론과 근거 ID를 전달하고, 중요한 최종 주장만 원문과 다시 대조한다.

토큰 한도는 호출 크기를 정하는 실행 제약이다. 특정 문서나 쟁점을 버리는 처리 기준이 아니다. 한 단위가 커지면 분할하고, 일부가 실패하면 해당 단위만 `UNREVIEWED`로 남긴다.

## 새 처리 흐름

| 단계 | 최소 작업 단위와 입력 | 저장할 결과 | 합치는 방법 |
|---|---|---|---|
| 0. 자료 등록 | 조문 항·호·단서, 판례 명제, 문서 문단을 ID·원문 해시로 등록 | 전체 단위 목록과 부모·참조 관계 | 모든 원문 단위에 `PENDING` 행을 만든다 |
| 1. 쟁점 후보 | 문서 조각 1개와 짧은 질의·검토 유형 | 사실 후보, 쟁점 후보, 출처 ID | 중복을 합치되 출처·상충 후보를 보존한다. 모든 문서 조각을 처리했는지 확인한다 |
| 2. 근거 조사 | 쟁점 1개와 사실 ID·검색 후보 ID | 관련 근거 ID, 반대 근거 ID, 누락·검색 실패 | 쟁점별 근거 묶음을 만든다. 검색 실패는 빈 근거와 구분한다 |
| 3. 요건 분해 | 조문 1개 또는 그 항·호·단서 묶음. 사건 접두부는 사용하지 않음 | 원자적 요건, 선택·누적 관계, 예외, 원문 ID | 조문별 요건 그래프로 합친 뒤 원문 단위의 반영 여부를 점검한다 |
| 4. 사실 포섭 | 쟁점 × 요건 1개, 관련 사실과 그 출처, 해당 요건 원문 | 충족·불충족·불명, 양측 근거, 이유, 결여 사실 | 모든 필수 요건과 예외의 결과를 규칙으로 합쳐 쟁점 결론을 만든다 |
| 5. 주장 검증 | 주장 × 근거 원문 1쌍 또는 작은 묶음 | `SUPPORTS/PARTIAL/NOT_SUPPORTED/UNKNOWN`, 인용 위치 | 주장별 검증 원장을 합친다. 유사도는 순서만 정한다 |
| 6. 최종 조립 | 검증을 통과한 쟁점 결론 카드 소수 | 사건 요약, 조건부 결론, 남은 공백 | 여러 차례 계층적으로 요약하되 원래 카드 ID로 역추적한다 |

### S3 분할·병합 규칙

1. 첫 호출은 **조문 1개**와 그 조문에 속한 하위 원문만 보낸다. 사건 질의, 첨부문서, 다른 조문 색인은 보내지 않는다. 출력은 요건별 `sourceIds`와 `relation`(`ALL/ANY/EXCEPTION`)을 요구한다.
2. 입력이 작업 예산을 넘으면 항 단위로 나눈다. 항 안의 호가 길면 호 단위로, 단서가 길면 단서의 문장 단위로 나눈다. 원문 순서와 부모 ID를 유지한다. **단일 원문 단위조차 길면** 문장 경계에서 창으로 나누고, 겹치는 앞뒤 문맥과 원문 오프셋을 기록한다.
3. 하위 결과를 조문 단위로 합칠 때 중복 요건만 병합한다. `모두 충족`과 `하나 충족`, 원칙과 단서는 코드가 임의로 추론하지 않는다. 관계가 불분명하면 별도 작은 LLM 호출로 해당 연결 문구와 하위 카드만 제시해 판단한다.
4. 원문의 모든 단위가 정확히 한 번 이상 요건 카드에 연결되는지 확인한다. 모델이 원문에 없는 요건을 만들거나 출처 ID를 틀리면 해당 카드만 재시도한다. 골격 추출은 복구용 초안이며 `DECOMPOSITION_UNVERIFIED`로 표시한다.
5. 캐시 키는 조문 원문 해시, 시행 시점, 분해 프롬프트 버전, 분할 방식 버전, 모델을 포함한다. 성공한 하위 단위는 재실행 시 재사용한다.

### S4·S6의 작은 판단

- S4는 쟁점 전체를 한 번에 판단하지 않는다. `쟁점 ID × 요건 ID`마다 필요한 사실과 1~3개의 근거 명제만 로드한다. 선결 쟁점은 원문 대신 검증된 결론 카드와 상태를 전달한다. 전체 요건 결과를 합칠 때 필수 요건 하나가 불명이라도 확정 결론을 만들지 않는다.
- S6는 검증할 모든 주장·근거 쌍을 작업 대기열에 넣는다. 12쌍까지만 처리하는 전역 절단을 없애고, 배치가 예산을 넘으면 절반으로 분할한다. 그래도 넘으면 한 쌍으로 처리한다. 하나의 근거 원문이 너무 길면 명제 또는 문장 단위로 나누고 정확한 오프셋을 저장한다. 핵심 전후 문맥을 같이 주되 원문 누락이 생기면 `UNKNOWN`으로 둔다.
- 존재, 공식성, 적용 시점은 코드로 먼저 검사한다. 임베딩은 검증 우선순위와 관련 문장 찾기에만 쓴다. `SUPPORTED`는 원문에 대한 함의 확인 또는 명시적이고 감사 가능한 결정 규칙을 통과해야 한다. 판정 실패·시간 초과·토큰 초과는 `UNKNOWN`이며 지지로 바꾸지 않는다.
- 결론을 뒤집는 핵심 주장과 예외·반대 근거를 우선 처리하되, 완료 상태를 선언하려면 대기열이 비어 있어야 한다. 사용자가 중단하면 미처리 쌍을 원장에 남긴다.

## 호출 예산과 복구

- 각 호출 전에 **최종 시스템 지시문 + 작업 입력 + 출력 예약 + 계수 오차 여유**를 측정한다. 작업 입력 목표치는 입력 한도의 약 60~70%로 두고 나머지는 계수 오차, 재시도 피드백, 긴 인용에 남긴다. 이 비율은 운영 설정이며 실측으로 조정한다.
- `INPUT_BUDGET_EXCEEDED`이면 같은 프롬프트를 다시 보내지 않는다. 작업 단위를 분할한다. 분할 불가능한 최소 단위는 `OVERSIZE_UNREVIEWED`로 기록한다. 네트워크·형식 오류는 해당 단위만 제한 횟수 재시도한다.
- 작업마다 `jobId, parentId, sourceIds, inputHash, promptVersion, status, attempts, tokenCount, outputHash`를 저장한다. 완료된 하위 작업은 재시작 시 건너뛰고 실패한 단위부터 다시 실행한다. 총 호출 수와 총 시간에는 운영 상한을 두되, 상한에 걸리면 남은 작업 수를 표시하고 부분 결과로 끝낸다.
- 입력이 길어서 버린 원문, 처리하지 않은 조문, 미검증 주장, 출력 절단은 각각 개수와 ID를 기록한다. 품질 게이트는 단순 `경고 문자열`이 아니라 구조화된 작업 상태를 검사한다.

## 완료 판정

`COMPLETE`는 (1) 등록된 입력 단위의 쟁점 추출 완료, (2) 필요한 조문 요건 분해 검증 완료, (3) 모든 핵심 요건 포섭 완료, (4) 결론에 사용한 근거·주장 쌍의 검증 완료, (5) 선결 쟁점·예외·반대 근거 처리 완료일 때만 허용한다. 하나라도 미처리면 `PARTIAL`과 미처리 ID를 표시한다. 근거가 실제로 부족한 경우는 `UNREVIEWED`와 구별해 `INSUFFICIENT_EVIDENCE`로 남긴다.

최종 문서는 쟁점별 작은 결론을 합성하되, 결론마다 요건 카드 → 사실 ID → 공식 근거 ID → 원문 위치를 역추적할 수 있어야 한다. 상위 요약이 하위 결론의 확실성을 높이지 못하도록 상태는 가장 약한 필수 하위 상태를 따른다.

## 구현 순서와 검증 기준

1. `elements.js`, `warrant.js`에서 거대한 공통 접두부 의존을 제거하고 조문·쌍 단위 입력으로 전환한다. S6의 12쌍 절단과 유사도만으로 지지 처리하는 경로를 없앤다.
2. 공통 `workQueue`와 적응형 분할기를 만들고, S1·S3·S4·S6에 순차 적용한다. 기존 근거 등록부와 `runStage` 예산 계수는 재사용한다.
3. `pipeline.js`의 품질 게이트를 구조화된 커버리지 원장으로 바꾸고, S5는 완료된 카드만 합성한다. UI에는 `미처리 조문/요건/주장` 수와 ID를 보여준다.
4. 재현 시험: 이번 사례의 35,346/30,208 및 38,051/31,232 입력을 같은 모델 설정으로 다시 실행한다. **최대 개별 호출 입력은 한도 미만, S3 골격 대체 0건, S6 미처리 쌍 0건**을 목표로 한다. 긴 단일 조문, 12쌍 초과, 분할 중 형식 오류, 서버 재시작, 예외와 반대 근거 누락도 각각 시험한다. 총 호출·토큰·시간과 검토 품질은 기존 사례 기준선과 함께 기록한다.

호출 수와 총 처리 시간은 늘 수 있다. 대신 입력 크기가 사건 전체 길이에 따라 증가하지 않으며, 어느 부분까지 검토했는지 확인하고 실패한 작은 단위만 다시 처리할 수 있다.

## 구현 현황 (2026-09-24)

- S1은 공통 입력에서 문서 조각이 빠지거나 입력 예산을 넘으면 질의 구간과 문서 조각으로 나눈다. 분할 중에도 예산을 넘는 묶음은 다시 절반으로 나눈다. 미처리 구간과 문서 ID를 기록한다.
- S3은 조문별·항호단서 묶음별로 호출하고, 예산을 넘는 원문은 문장 경계 또는 절반으로 더 나눈다. 일부만 골격으로 보충한 조문은 `PARTIAL`, 전부 골격이면 `SKELETON`이며 성공 캐시에 넣지 않는다.
- S4는 한 번에 요건 최대 4개와 해당 쟁점의 사실만 싣는다. 긴 근거는 하위 단위 또는 원문 오프셋 조각으로 나눈다. 미처리 근거가 있으면 쟁점은 `PARTIAL` 및 판단 유보가 된다.
- S6은 12쌍 상한을 제거하고 모든 주장·근거 쌍을 개별 확인한다. 긴 근거는 전부 조각으로 나누고, 유사도만으로 `SUPPORTED`를 부여하지 않는다. 실패한 쌍과 근거 없는 주장도 원장에 남기며 최종 결론을 판단 유보로 낮춘다.
- S5 종합과 수정 조문 호출은 사건 전체 접두부를 받지 않는다. 수정 대상 5개 상한을 제거했다. 생성 실패는 검토 게이트에 반영한다.
- 회귀 시험은 긴 조문, 12쌍 초과, 긴 근거, 10개 초과 요건, 긴 질의와 재검토를 포함한다.

남은 작업: 실행 도중 프로세스가 종료됐을 때 S4·S6의 완료 작업을 영속 저장해 이어서 실행하는 기능, 실제 운영 모델에서의 처리 시간·법리 품질 비교, 긴 수정 조문을 문단별로 고친 뒤 합치는 기능. 현재는 완료된 조문의 S3 캐시와 이전 검토의 쟁점 재사용만 적용된다.
