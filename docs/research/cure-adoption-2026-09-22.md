## 1. 권고

**CURE의 누적 지식 재사용 원리를 적용할 가치는 높다. 이 프로젝트에는 ‘검증된 쟁점별 검토 지식 + 소형/대형 모델 선택 실행’ 형태로 도입하는 것이 적합하다.**

첫 단계에서는 과거 검토에서 확인한 검색 경로, 적용 요건, 예외 점검표를 재사용한다. 이후 평가를 통과한 좁은 유형부터 로컬 모델만으로 검토 초안을 생성한다. 비슷한 질문이라는 이유로 과거 결론을 그대로 반환하는 방식은 권고하지 않는다.

현재 프로젝트에는 공식 근거 수집, Ollama와 클라우드 모델 호출, SQLite, 검토 이력, 인용 검증이 이미 있다. 추가해야 할 핵심은 지식의 승인·검색·무효화, 사실관계의 차이 검사, 실행 경로 선택, 전체 호출량 측정이다. 초기 실험에 모델 재학습이나 별도 벡터 DB 서버는 필수가 아니다.

효용은 운영 방식에 따라 달라진다. 현재처럼 제공자를 선택하는 구조에서 클라우드 모델을 자주 사용한다면 호출비 절감 여지가 있다. **Ollama만 사용하는 운영에서는 줄일 클라우드 호출이 없으므로**, 기대 효과는 검토 일관성·근거 탐색 개선이며 속도 개선은 별도 측정해야 한다. 두 경우 모두 이 보고서의 효과는 가설이다.

## 2. 원 기술에서 확인한 사실과 적용의 경계

기사의 CURE는 KAIST 연구팀의 기기–서버 협업 기술이다. 기기 모델의 판단, 누적된 지식 활용, 서버 위임 순으로 처리하며 모델을 재학습하지 않고 지식을 축적한다. 검증에 사용한 조합은 MobileCLIP2와 EVA-CLIP-18B다. [기사 원문](https://www.aitimes.kr/news/articleView.html?idxno=42013), [KAIST 공식 발표](https://news.kaist.ac.kr/news/html/news/?mng_no=67310&mode=V)

공개 보충자료의 Algorithm 1에서는 두 단계의 불확실성 라우팅, reservoir 갱신, 예측 결합을 확인했다. 첫 판단과 누적 지식의 판단이 각각 기준을 통과하는지 검사하고, 부족할 때 서버를 호출한다. 임계값은 엔트로피 이력과 서버 판단과의 불일치 이력을 활용한다. 이는 과거 응답 문자열의 단순 캐시와 구별된다. [논문 보충자료, Algorithm 1](https://media.springernature.com/original/springer-static/esm/chp:10.1007%2F978-3-032-37627-5_21/MediaObjects/700373_1_En_21_MOESM1_ESM.pdf)

| 발표 수치 | 비교 대상 | 해석 |
|---|---|---|
| 서버 호출 평균 55.61% 감소 | 지식을 누적하지 않는 기존 협업 방식 | KAIST 발표 수치 |
| 서버 위임 평균 66.74% 감소 | 모든 입력을 서버로 보내는 방식 | 논문 초록 수치 |
| 실행시간 최대 3.67배 개선 | 모든 입력을 서버로 보내는 방식 | 특정 실험에서의 최대치 |

55.61%와 66.74%는 비교 기준이 다르다. 논문 초록은 13개 데이터셋의 결과를 보고한다. **어느 수치도 한국어 법률 검토에서 재현된 결과는 아니다.** [KAIST 공식 발표](https://news.kaist.ac.kr/news/html/news/?mng_no=67310&mode=V), [논문 초록](https://link.springer.com/chapter/10.1007/978-3-032-37627-5_21)

이 연구의 평가 대상은 이미지 분류다. 법률 의견서 생성은 정해진 클래스 중 하나를 고르는 작업과 달리 사실관계, 시점, 적용 요건, 문서 전체의 예외를 다룬다. 따라서 분류 확률의 엔트로피 임계값을 LLM이 말하는 ‘확신도 90%’로 치환할 근거가 없다. 아래 제안은 **CURE 원리를 응용한 별도 설계**이며 원 알고리즘을 그대로 이식한 구현이 아니다. [평가 데이터셋 및 알고리즘](https://media.springernature.com/original/springer-static/esm/chp:10.1007%2F978-3-032-37627-5_21/MediaObjects/700373_1_En_21_MOESM1_ESM.pdf)

2026-09-22 확인한 연구팀의 공개 GitHub 저장소에는 README와 Apache-2.0 LICENSE만 보였고 실행 코드는 확인되지 않았다. 따라서 현재 공개 상태를 기준으로 ‘패키지를 설치해 연결’하는 계획은 세울 수 없다. 원 논문 본문 전체는 확보하지 못했으며, 세부 수학식과 전체 실험표의 독립 재현은 이번 조사 범위에 포함하지 않았다. [연구팀 저장소](https://github.com/kaist-dmlab/CURE), [학회 발표 페이지](https://eccv.ecva.net/virtual/2026/poster/5036)

README의 기능 설명뿐 아니라 현재 소스를 기준으로 판단했다. 조사 당시 생성·컨텍스트·테스트 파일 등에 기존 미커밋 변경이 있었으며, 이 보고서는 그 상태를 포함한다.

## 4. 권장 처리 흐름

```text
질의·첨부문서·검토 기준일
         ↓
문서 파싱 / 필수 사실 추출 / 공식 근거 수집
         ↓
경량 로컬 판단: 쟁점과 누락 사실 확인
         ↓
승인 지식 검색 + 법령 버전·관할·사실·예외 조건 검사
         ↓
  재사용 가능하고 검증된 유형인가?
       ├─ 예 → 현재 공식 근거 + 참고 지식으로 로컬 초안 생성
       └─ 아니오 → 정책상 허용된 강한 모델로 위임
         ↓
공통 출력 검사 / 인용 존재 검사 / 주장-근거 연결 검사
         ↓
결과 + 실행 경로 + 재사용 범위 + 제한 사항 표시
         ↓
지식 후보 추출 → 검토·승인 → 다음 요청에서 검색 가능
```

최종 단계에서는 지식 없이도 검증 가능한 좁은 과제에 로컬 단독 경로를 허용할 수 있다. 초기에는 법률 결론 전체에 이 경로를 열지 않고 조문 식별·쟁점 정리 등에 한정한다. 매 요청마다 긴 로컬 의견서를 먼저 작성하고 다시 로컬 의견서를 쓰는 구조도 피한다. 앞단은 짧은 구조화 작업, 본 생성은 가능한 한 한 번으로 설계하고 실패 시에만 강한 모델을 추가 호출한다.

‘강한 모델’은 승인된 클라우드 제공자 또는 더 큰 사내·로컬 모델이다. 로컬 전용 설정에서 자동으로 클라우드로 바뀌어 첨부문서가 전송되지 않도록 실행 정책을 명시해야 한다. 기존 모델 선택 동작도 유지하고, 자동 경로는 별도 모드로 제공한다.

재사용으로 절감하려는 대상은 우선 **대형 모델 호출**이다. 현행·과거 기준에 맞는 공식 근거 확보는 각 요청에서 계속 수행하고, 기존 공식 자료 캐시는 그 유효성 정책 안에서 사용한다. 지식에 저장된 과거 설명을 최신 법령 조회의 대체물로 삼지 않는다.

## 5. 무엇을 기억할 것인가

저장 단위는 전체 의견서보다 **쟁점별 지식 카드**가 적합하다. 모델의 비공개 내부 추론을 요구하지 않고, 검토자가 확인할 수 있는 적용 요건·근거·짧은 설명·점검 절차를 저장한다.

| 필드 그룹 | 예시 및 목적 |
|---|---|
| 식별·출처 | 카드 ID, 원 검토 ID, 쟁점 ID, 생성 시각, 검토자·승인 시각 |
| 적용 범위 | 프리셋, 쟁점 유형, 관할 지자체·기관, 현재/과거 검토 구분 |
| 사실 조건 | 필수 사실, 중요 수치·기간·행위 유형, 적용 제외 조건, 확인해야 할 사실 |
| 근거 | 법령 ID·버전·시행일·조항, 인용 원문 해시, 판례·해석례 식별자, 수집 시각 |
| 재사용 내용 | 검색어·조회 경로, 적용 요건 점검표, 예외 확인 순서, 짧은 근거 설명 |
| 품질 | 승인 상태, 검증 범위, 정답 대조 결과, 실패·사용 횟수 |
| 호환성 | 생성 모델, 임베딩 모델·버전, 프롬프트·스키마 버전 |
| 수명·격리 | 유효 기간, 폐기 사유, 로컬 작업공간/조직 구분, 삭제 대상 출처 |

권장 상태는 `CANDIDATE → APPROVED → STALE / REVOKED`다. API 실패, 목업, 규칙 폴백, 출력 잘림, 미검증 인용, 근거 부족 결과는 자동 승인하지 않는다. 전체 검토가 `PARTIAL`인 경우 초기에는 자동 후보 승격도 막고, 나중에 쟁점별 검증 범위를 표현할 수 있을 때 제한적으로 허용한다.

예를 들어 ‘공유재산 사용료 산정’의 이전 검토에서 모법·시행령·해당 지자체 조례·고시·별표를 확인한 순서와 예외 요건 목록은 재사용할 수 있다. 새 사안의 지자체, 재산 분류, 산정일, 예외 요건이 다르면 이전 비율이나 수용·반려 결론은 가져오지 않는다. 이는 적용 방식의 예시이며 특정 사안의 법적 결론이 아니다.

## 6. 검색과 재사용 허용 기준

검색과 답변 채택은 서로 다른 판단으로 구현한다.

**먼저 적용 범위를 거른다.** 작업공간·승인 상태·검토 유형·법령 및 버전·관할·기준일 범위가 맞는 카드만 후보로 둔다. 이후 키워드 검색과 선택적 로컬 임베딩으로 비슷한 쟁점을 찾는다. 소규모 PoC에서는 SQLite의 구조화 필터와 텍스트 검색으로 시작할 수 있으며, FTS5 지원 여부는 실제 Node/SQLite 런타임에서 확인한다. 임베딩은 한국어 법률 문장과 부정·수치·예외의 최소 차이에서 평가한 뒤 선택한다.

**그다음 적용 조건을 검사한다.** 의미 유사도는 검색 순위에만 쓴다. 조건 일치, 필수 사실의 완비, 현재 원문 근거 확보, 예외 검토, 근거 간 충돌 여부를 별도 기록한다. 필수 사실을 확인하지 못한 경우 ‘일치’로 추정하지 않고 추가 확인 또는 위임 사유로 남긴다.

초기 로컬 재사용 허용 조건은 다음을 모두 충족하는 보수적 규칙을 권고한다.

- 해당 쟁점 유형이 전문가 평가를 통과한 허용 목록에 있다.
- 카드가 승인 상태이고, 관련 법령·조례·고시·판례 등 의존 자료가 요청의 시점과 호환된다.
- 핵심 사실과 수치·기간·관할이 맞고, 미확인 필수 사실과 충돌하는 근거가 없다.
- 쟁점 판단에 필요한 문서 구간과 예외·단서가 확보되어 있다.
- 새 결과의 인용 및 주장-근거 검사가 통과한다. 법적 판단을 자동 확정하는 별도 권한은 부여하지 않는다.

조문이 존재한다는 점수, 판례 재정렬 점수, LLM의 자기 확신도 하나로 클라우드 호출을 생략하지 않는다. 강한 모델과의 일치율도 전문가 정답을 대신하지 못한다. 보정 기준과 허용 목록은 별도 검증 데이터로 정하고 운영 중 오류를 발견하면 해당 카드를 회수한다.

## 7. 무효화와 문서 범위 관리

단순 TTL만으로는 법령 변경을 처리하기 어렵다. 카드와 근거 사이의 의존 관계를 저장하고, 사용 직전에 기준일에 맞는 버전·원문 해시를 대조한다. 법령뿐 아니라 연결된 시행령·규칙·조례·고시·별표·판례·해석례도 포함한다. 필요한 자료가 없거나 변경 의미를 판정할 수 없으면 재사용을 보류한다.

현행 조문이 바뀌었다고 과거 사건용 카드를 모두 삭제할 필요는 없다. 과거 버전을 보존하되 그 버전이 적용되는 검토에만 사용할 수 있도록 분리한다. 부칙과 경과조치가 불명확하면 버전 일치만으로 충분하다고 판단하지 않는다.

메모리에 있는 내용은 참고 자료로 표시하며 공식 근거 배열에 합치지 않는다. 모델에는 공식 원문과 기억의 우선순위를 구분해 제공하고, 기억의 설명과 현재 원문이 충돌하면 원문 재검토 경로로 보낸다. 과거 사용자 문서에 들어 있던 지시문이 재사용 시 시스템 지시로 승격되지 않도록 카드 스키마를 제한한다.

기본 저장은 로컬로 두고 민감한 원문 대신 필요한 최소 사실·출처를 보존한다. 검색 임베딩도 데이터로 취급한다. 원 검토를 삭제했을 때 관련 후보·카드·인덱스까지 삭제 또는 회수할 수 있도록 출처 ID를 연결한다. 조직 단위 공유는 사용자 인증·권한이 마련된 이후의 범위다.

## 8. 구현 단위

아래 파일명과 설정은 **제안이며 현재 구현되어 있지 않다.**

| 변경 대상 | 제안 작업 |
|---|---|
| 신규 `server/law/knowledgeMemory.js` | 별도 `legal_knowledge.db`, 카드·근거 의존성·승인 상태·검색·회수 |
| 신규 `server/law/memoryApplicability.js` | 기준일·관할·사실·예외·근거 변경 검사; 구조화된 허용/거절 사유 |
| 신규 `server/law/hybridReviewRouter.js` | 명시적 실행 정책, 경량 로컬 처리, 기억 활용, 위임, 실패 처리 |
| 신규 `server/law/llmCalls.js` | 요청별 모든 생성·계수·재시도 호출의 제공자/모델/시간/사용량 기록 |
| 기존 `lawWorkbenchReview.js` | 내부 제공자 호출을 공통 어댑터로 정리; 좁은 조문 식별 단계의 검증 강화 |
| 기존 `reviewContext.js`, `llmBudget.js` | 기억의 독립 예산, 추가 후 최종 입력 계수, 원문 근거 최소 예산 보호 |
| 기존 `lawApi.js` | 라우터 연결, 응답에 실행 경로·재사용 카드·제한·호출 합계 추가 |
| 기존 화면·이력·내보내기 | 재사용 범위와 기준일, 부분 검토 상태를 동일하게 표시 |
| 신규 평가 하네스 | 동일 사례군의 순차 입력, 반례, 법령 변경, 비용·지연 비교 |

`review.execution`에는 예를 들어 `mode`, `route`, `memoryIds`, `rejectionReasons`, `calls[]`, `totals`를 둔다. 제공자 사용량이 누락되면 0원·0토큰으로 간주하지 않고 측정 불가로 남긴다. `tokenUsage` 단일 필드를 덮어써 앞선 호출을 잃지 않도록 한다.

초기 정책은 `off / shadow / assist / hybrid` 정도로 구분한다. `shadow`는 실제 판단에 반영하지 않고 일치·거절 여부를 기록하고, `assist`는 검증된 지식을 프롬프트 참고로 제공하며, `hybrid`에서만 평가를 통과한 유형의 대형 모델 호출 생략을 허용한다.

## 9. 실험 설계와 비용 판단

기존 20건은 회귀 점검의 출발점으로 쓰되 법률 품질 입증에 충분한 표본으로 보지 않는다. 초기 파일럿은 반복 업무 1~2개 유형, 전문가가 확인한 지식 카드 약 30~50개, 평가 질의 약 200개 수준을 계획할 수 있다. 이는 일정·규모 가정이며 통계적 안전성 보장 수치가 아니다.

비교군은 동일 모델·근거 스냅샷·출력 형식·장비 조건으로 구성한다.

| 비교군 | 확인하려는 효과 |
|---|---|
| 현재 선택 제공자 경로 | 실제 운영 대비 변화 |
| 항상 강한 모델 사용 | 품질·비용의 비교 기준; 정답 자체는 전문가 기준 |
| 완전 일치 응답 캐시 | 단순 반복 요청 캐시와의 차이 |
| 소형→대형 선택 실행, 기억 없음 | 실행 경로 선택만의 효과 |
| 승인 지식 + 선택 실행 | 지식 축적이 추가로 주는 효과 |

이미 알려진 업무 유형의 유사 질의를 시간 순으로 넣는 평가와, 완전히 새로운 업무 유형의 평가를 분리한다. 임계값 조정용 사례와 최종 평가 사례도 분리한다. 정답·미래 사례·미승인 결과가 평가 전에 메모리에 들어가지 않도록 한다. 빈 저장소에서 시작한 경우와 승인 지식이 쌓인 경우를 각각 측정하고, 지식 생성에 쓴 호출량도 포함한다.

반드시 포함할 반례는 ‘문장은 비슷하지만 결론이 달라질 수 있는’ 입력이다. 지자체만 다른 조례, 개정일 전후, 원칙과 단서, 동의 유무, 수치·기간의 변경, 의무와 재량, 핵심 사실 누락, 과거 검토 오류의 정정, 긴 문서의 제외 구간, 외부 호출 실패를 넣는다. 문서 내용의 지시문 주입과 다른 작업공간의 기억 검색도 검사한다.

핵심 측정치는 전문가 채점의 쟁점 누락·포섭 타당성·중요 오류, 검증된 인용 precision/recall, 부적절한 재사용률, 판단 보류율, 전체 클라우드 호출 수, 제공자별 실제 토큰, p50/p95 지연이다. 전문가 검토는 실행 경로를 가린 상태에서 비교하는 것이 좋다. 호출 감소율만 높고 오류나 보류가 늘어난 실험은 성공으로 판단하지 않는다.

초기 도입 기준의 예시는 ‘중요 오판이 발견되면 해당 유형의 자동 재사용 중단, 전문가 품질이 사전 합의한 비열등 기준을 충족, 반복 사례군에서 호출비 또는 p95 지연이 실질적으로 개선’이다. 표본에서 오류가 0건이었다고 오류 확률이 0이라고 해석하지 않고 불확실성을 함께 보고한다. 구체적인 임계값과 표본 수는 운영상 허용 오류 수준에 맞춰 정한다.

경제성은 다음처럼 계산한다. `p`는 강한 모델로 위임하는 비율, `C_T`는 항상 강한 모델을 쓸 때 요청당 비용, `C_L`은 경량 로컬 처리와 로컬 생성의 평균 비용, `C_M`은 검색·유효성 검사 비용, `C_V`는 추가 검증 비용, `C_K`는 카드 생성·승인 비용을 사용 횟수로 나눈 값이다.

```text
하이브리드 요청당 비용 ≈ C_L + C_M + p × C_T + C_V + C_K
절감 조건             : (1 - p) × C_T > C_L + C_M + C_V + C_K
```

실제 위임 프롬프트가 길어지면 위임 시의 `C_T`를 별도로 측정해야 한다. 클라우드 API 청구액과 로컬 장비·전력·검토 인건비를 포함한 총운영비도 구분한다. 로컬 선처리 뒤 위임되는 요청은 기존보다 느려질 수 있어 평균뿐 아니라 p95와 경로별 시간을 본다. 순수 Ollama 운영에서는 비용 절감보다 품질 유지와 추가 지연 여부가 우선 평가 대상이다.

## 10. 단계별 도입안

아래 공수는 개발자 1명과 필요한 전문가 검토가 가능하고 기존 실행 환경을 사용할 수 있다는 가정의 추정이다. 외부 API 응답 시간, 사례 확보, 전문가 승인 대기, 모델·장비 선정은 별도다.

| 단계 | 산출물 | 개발 공수 추정 |
|---|---|---|
| 0. 측정 기반 | 모든 호출의 시간·사용량 원장, 최종 프롬프트 계수, 기존 경로 기준값 | 1~2일 |
| 1. 제한적 지식 재사용 | 별도 DB, 카드 승인·회수, 구조화 검색, 참고 지식 주입, 버전 검사 | 3~5일 |
| 2. 관찰 모드 | 소형/강한 모델의 경로 비교, 사실 차이 검사, 반례 평가 | 3~5일 |
| 3. 제한적 자동 선택 | 허용 유형만 호출 생략, 운영 표시·중단·회귀 검증 | 3~5일 |

전체는 대략 **10~17 개발일 + 전문가 평가 기간**을 첫 계획 범위로 잡을 수 있다. 처음부터 일곱 프리셋 전체에 적용하지 않고, 사용 빈도가 높고 적용 조건을 명확히 표현할 수 있는 쟁점부터 시작한다. 사전 컨설팅감사에서 기억은 조문 식별·예외 점검을 돕는 용도로 먼저 쓰고, 최종 수용·반려 판단의 호출 생략은 뒤로 둔다.

가장 먼저 구현할 묶음은 **호출량 측정 → 승인된 지식 카드 저장 → 현재 공식 근거와 함께 참고로 제공 → 반례 평가**다. 이 단계에서 품질과 반복 이용 빈도가 확인된 뒤 대형 모델 호출 생략을 켜는 순서가 적절하다.

## 11. 조사 범위와 산출물

기사 원문, KAIST 공식 발표, Springer 논문 초록과 공개 보충자료, ECCV 발표 페이지, 연구팀 GitHub 공개 상태를 확인했다. 소스 분석으로 현재 구조와 연결 지점 및 평가상 주의사항을 도출했다. 원 연구의 내부 구현 재현, 한국어 법률 품질 실측, 로컬 장비 성능 측정, 유료 모델 호출은 수행하지 않았다.

프로젝트의 애플리케이션 코드·설정·기존 데이터는 변경하지 않았으며 이 연구 보고서만 추가했다. 기존 문서의 과거 성능 홍보 수치는 적용 효과의 근거로 사용하지 않았다.
