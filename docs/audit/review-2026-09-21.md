## 판단

제공된 보고서의 핵심 결함 진단과 두 가지 처방에 대한 반대는 타당하다. 그러나 **“허위 신뢰도 문제가 걷혔다”는 총평에는 동의할 수 없다.** 현재 코드에도 잘못된 인용을 100% 검증 완료로 만들고, 빈 LLM 응답을 정상 검토로 승인하고, 내보내기에서 경고를 제거하거나 근거를 만들어 넣는 경로가 있다.

개선 순서는 먼저 검증·완료 판정과 내보내기의 신뢰성을 복구한 다음, 문서 및 법령 본문을 LLM에 정확하게 연결하는 것이 적절하다. 장문 컨텍스트 연결만 먼저 고쳐도 근거의 신뢰성을 보장할 수 없다.

### 2. P1 — 빈 LLM 응답을 검토 완료·검증 100%로 승인한다

근거: [lawWorkbenchReview.js:461](D:/Dev/legal_review/server/law/lawWorkbenchReview.js:461).

LLM 응답을 `{}`로 대체하고 컨텍스트에 조문 한 개를 넣으면 다음 결과가 나온다.

```json
{"isFallback":false,"summary":"검토가 완료되었습니다.","legalOpinion":"","addedCitations":1,"citationConfidence":100}
```

`normalizeReviewResult()`는 JSON 파싱 성공만으로 LLM 결과를 승인하고, 빈 `legalBasis`를 검색 결과에서 자동 생성한다. 그 생성 항목을 같은 검색 결과로 다시 검증하므로 순환 검증이 된다. 잘린 JSON 복구 결과도 필수 내용·완결성 판정 없이 정상 처리될 수 있다.

개선: 응답 스키마와 필수 본문을 검증하고 `COMPLETE/PARTIAL/FAILED` 상태를 분리한다. 검색 결과는 참고자료로 유지하되 모델이 실제 인용한 근거로 둔갑시키지 않는다. 절단 복구 여부와 생성 종료 사유를 보존한다.

완료 기준: `{}`, `[]`, 필수 항목 없는 객체, 잘린 JSON을 성공 검토로 표시하지 않으며 자동 보강한 근거가 모델 인용 정확도를 올리지 않는다.

[연혁 목록 가이드](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsHstListGuide), [시행일 목록 가이드](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdListGuide), [시행일 본문 가이드](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdInfoGuide).

### 7. P1 — 이름이 비슷한 법령을 다른 법령으로 치환한다

근거: [lawWorkbench.js:57](D:/Dev/legal_review/server/law/lawWorkbench.js:57), [lawWorkbench.js:93](D:/Dev/legal_review/server/law/lawWorkbench.js:93).

명시 인용도 법령별로 묶지 않고 모든 조문 번호를 한 집합으로 합친 다음 주 법령에서 찾는다. 복수 법령 검토에서 서로 다른 법령의 동번호 조문이 섞일 수 있다.

개선: 법령 ID와 정규화한 정식 명칭·검증된 별칭으로 일치 여부를 확인한다. 모법·시행령·시행규칙은 별도 엔터티로 취급한다. 복수 법령 인용은 법령별로 수집하고 검증한다.

## 추가 개선 사항

### 판례뿐 아니라 유권해석에도 본문 수집이 필요하다

`searchInterpretations()`도 목록만 조회한다. 상세 조회를 추가할 때 기존 목록 파서를 그대로 쓰면 안 된다. 공식 상세 필드는 `법령해석례일련번호`, `해석일자`, `회답`인데 현재 매핑은 `해석례일련번호`, `회답일자`, `회답요지` 중심이다. [법령해석례 본문 명세](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=expcInfoGuide).

판례 본문은 `lawService.do?target=prec&ID=<판례일련번호>`로 조회하고 `판시사항`, `판결요지`, `판례내용`, 참조조문을 정규화해야 한다. 상세를 확보한 후보를 재평가하되 실패·빈 본문을 명시한다. [판례 본문 명세](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=precInfoGuide).

### cascadingRetriever는 현재 명칭 검색 묶음에 가깝다

[cascadingRetriever.js:12](D:/Dev/legal_review/server/law/cascadingRetriever.js:12)에서 `articleNos`를 사용하지 않고, 검색 상위 6건에서 종류별 첫 결과를 고른 뒤 시행령 앞 3조·규칙 앞 2조를 가져온다. 모법 해당 조항의 위임 관계를 추적하지 않는다.

본문이 빈 시행령과 모법 이름만 있어도 `isCompleteHierarchy:true`가 되는 것을 재현했다. 시행규칙이 실제로 없는 법률도 있으므로 “모든 법령에 3단계가 존재해야 한다”는 완료 기준도 잘못이다. 관계 확인·본문 확보·해당 단계 존재 여부를 각각 반환해야 한다.

테스트는 주입한 픽스처로 위임 관계, 무관한 동명 후보, 빈 본문, 없는 시행규칙, 페이지 밖 후보를 검증한다. 실제 API 통합 테스트는 자격증명 미설정 시 skip하되, 자격증명이 있는데 API가 실패하면 실패로 처리한다. 운영 목업을 채워 19/19를 맞추지 않는다.

### pre-warm 삭제에는 기존 데이터 정리도 포함해야 한다

### 벤치마크는 여전히 법리 품질 판정에 부족하다

[runBenchmark.js:39](D:/Dev/legal_review/test/benchmark/runBenchmark.js:39)의 인용 비교는 조문 번호 중심이다. 기준 법령은 컨텍스트 메타데이터를 별도로 검사하므로 개별 인용의 법령 정합성을 보장하지 않는다. `recall > 0`이면 PASS가 가능해 오인용이 다수 있어도 합격할 수 있다. 자동 보강한 `legalBasis`도 평가에 섞인다.

법령·버전·가지·항·호가 포함된 정답, 독립 전문가가 판정한 쟁점·결론·예외, 잘못된 인용 비율, 답변 보류의 적절성을 평가해야 한다. 검색·추론·내보내기 평가를 분리하고 인증된 실제 요청 수·캐시 적중·폴백·실패를 각각 기록한다.

### 배포 전 접근 통제와 데이터 보존 정책이 필요하다

[env.js:21](D:/Dev/legal_review/server/env.js:21)의 기본 바인딩은 `0.0.0.0`, [index.js:18](D:/Dev/legal_review/server/index.js:18)은 제한 없는 CORS이며, 이력 조회·삭제 라우트에는 인증 미들웨어가 없다. 네트워크에서 포트에 접근 가능한 배포라면 다른 사용자가 검토 이력을 읽거나 삭제할 수 있는 구조다. 외부 방화벽·프록시 배치는 확인하지 않았으므로 실제 인터넷 노출을 단정하지 않는다.

`.gitignore`에 WAL/SHM 패턴을 추가하는 것만으로 이미 추적되는 파일이 사라지지 않는다. 로컬 DB 보존을 전제로 추적 해제하고, 커밋된 WAL에 제거해야 할 데이터가 있는지는 별도 조사한다. 이번 검증에서 Git 인덱스나 DB는 정리하지 않았다.
