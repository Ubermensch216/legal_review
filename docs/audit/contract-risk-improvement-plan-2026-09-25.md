# 계약서 리스크 검토 개선 계획

기준일: 2026-09-25  
범위: `contract_risk` 단계형 검토와 그 결과를 쓰는 화면·보고서·재검토 경로

## 1. 목표와 확인된 현상

계약서에 실제로 있는 문언을 근거로 **조항 자체의 위험**을 제시하고, 법적 효력이나 실제 책임을 확정하는 데 필요한 추가 사실은 별도로 표시한다. 공식 법령·판례 검증과 `HUMAN_REVIEW_REQUIRED` 게이트는 유지한다.

첨부 검토 보고서가 설명한 8쪽 PDF의 문구와 누락 사항은 개선 요구사항으로 채택한다. 그 PDF 파일은 현재 저장소에 없으므로, PDF에 관한 개별 지적은 이 계획에서 독립 재현 사실로 취급하지 않는다. 샘플 계약 원문은 `test/generateReviewTestDocs.js`의 생성 정의와 `test/docs/review-samples/02_정보시스템_구축_용역계약서.docx`로 확인했다.

### 코드 대조 결과

| 지적 | 확인 결과 | 설계에 반영할 점 |
|---|---|---|
| 계약문언이 사실로 연결되지 않음 | `evidenceRegistry.js`는 D 문서를 등록하지만, `caseIssues.js`는 모델이 80자 이내 인용문과 fact를 다시 만들도록 한다. `issueResearch.js`의 `documentIds`도 이 fact 연결에서 유도된다. | D 조항·표의 원문 위치로부터 문서 사실을 결정적으로 생성하고 쟁점에 직접 연결한다. |
| 쟁점 5개 상한 | `pipeline.js` 기본값은 5, 환경변수로 올려도 최대 8이다. `caseIssues.js`는 초과 쟁점을 실제로 삭제한다. | 독립 쟁점을 삭제하지 않고, 처리·표시 우선순위와 미검토 상태를 분리한다. |
| 입증 부족이 곧 판단 유보로 바뀜 | `applyFactProvenance()`는 확인된 fact가 없으면 `proof`를 강등한다. **이 함수가 `status`를 직접 `UNKNOWN`으로 바꾸지는 않는다.** `CONDITIONAL`은 모델의 요건 상태, 선결 쟁점, 근거 검증, 단계 실패 등 여러 경로에서 발생한다. | 원인별 진단을 남기고, 문언 위험과 법적 효력을 별개로 계산한다. |
| 수정안 누락 | `draftRedlines()`는 `synthesis.risks`에서 HIGH/MEDIUM으로 선정되고 `documentIds`가 연결된 조항만 처리한다. | 검증된 문언 위험으로 수정안 후보를 결정하고, 합성 요약의 성공 여부에 의존하지 않게 한다. |
| 법률 조사 범위 | `issueResearch.js`는 S1 검색어를 쟁점별 2개, 전체 10개까지만 실제 조회한다. 쟁점 수만 늘리면 조사 누락이 늘 수 있다. | 법률 분야별 조문 후보와 조회 예산을 함께 설계한다. |
| 기존 실측 | `docs/audit/pipeline-comparison-2026-09-23.md`의 샘플 계약 측정은 5개 쟁점 모두 공식 요건 부재로 생략됐다. 이 측정은 첨부 8쪽 PDF와 동일 실행인지 확인되지 않았다. | 문서 사실 연결과 공식 근거 수집을 각각 독립된 품질 축으로 검증한다. |
| 실행 경로 | `docs/current-status.md`와 `lawWorkbenchReview.js`에 따르면 기본은 단일 호출이며 단계형은 설정 또는 입력 용량에 따라 사용된다. | 계약서 개선을 어디에서 사용하게 할지 별도 전환 기준을 둔다. 단계형 수정만으로 모든 계약 검토가 개선되지는 않는다. |

## 2. 구현 순서

### P0. 재현 기준과 자료 모델 확정

1. 샘플 계약을 동일 설정의 단계형 경로로 실행해 JSON, 모델 원장, PDF를 함께 보존한다. 쟁점 수, D 연결, 법령 연결, 수정안, 소요 시간, 토큰을 기준선으로 기록한다. 기존 8쪽 PDF가 제공되면 문구를 이 기준선과 대조한다.
2. `contract_risk` 전용 `ContractFinding`을 도입한다. 핵심 필드는 `sourceDocumentIds`, `sourceSpans`, `facialRisk`, `facialFinding`, `legalValidity`, `authorityEvidenceIds`, `additionalFactsRequired`, `reviewState`다. `sourceSpans`에는 조항뿐 아니라 별표의 표·행·셀 위치도 표현한다.
3. 문서 사실은 모델의 의역을 그대로 `CONFIRMED`로 승격하지 않는다. 원문 문자열 또는 검증된 오프셋·해시를 저장하고, 요약 문장은 별도 entailment 결과를 거쳐 표시한다. D 자료는 계약 내용의 출처이고 공식 법률 근거는 아니다.
4. `DOCUMENT_SUFFICIENT`는 **계약문언의 확인 상태**에만 사용한다. 약관성, 실제 지휘·명령, 손해 발생 등 문서 밖 사실의 충족 상태와 혼동하지 않는다.

**완료 조건:** 샘플 제7·11·14·17·19·22·25조와 지급표의 원문 위치가 파서 → D 등록부 → finding까지 추적된다. 존재하는 D를 두고 “내용 없음”이라고 쓰지 않는다.

### P1. 쟁점 탐지와 문언 위험 판단

1. S0 뒤에 계약 조항·별표 inventory를 만든다. 조항 번호가 없는 표와 부속서도 독립 후보로 다룬다. 기존 `RISK_PATTERNS`는 힌트로 사용하고 키워드 미일치가 삭제 사유가 되지 않게 한다.
2. S1은 inventory의 D ID를 직접 참조한다. 독립 쟁점의 하드 삭제를 없애고 긴 문서는 조항 묶음별 추출·중복 병합을 수행한다. 아직 조사하지 못한 후보는 `UNREVIEWED`로 남긴다. 최대 동시 처리량과 비용 한도는 별도 설정으로 관리한다.
3. 제11조의 지체상금과 별도 3배 위약벌처럼 법적 분류가 다른 약정은 하위 쟁점으로 나눈다. 제22조 인력 지휘, 제25조 분쟁절차, 지급표의 기한·조건을 탐지 범주에 넣는다.
4. 각 finding에 `facialRisk`와 `legalValidity`를 분리한다. 문언상 부담이 높다는 판단은 D 근거로 할 수 있지만, `LIKELY_INVALID` 등 법적 효력 표현은 공식 근거 및 적용 전제가 검증된 경우에만 허용한다. 기존 `conclusion.legal`은 다른 프리셋과의 호환을 위해 유지하고 계약 전용 결과에 두 축을 추가한다.

**완료 조건:** 샘플의 필수 8개 존재 쟁점이 모두 후보로 보존되고 각 쟁점이 D 조항 또는 표 위치와 연결된다. 쟁점 수를 늘린 뒤에도 S1 분할 결과가 누락 없이 병합된다.

### P2. 적용 법체계와 근거 조사

1. 일반 쟁점 수를 소비하지 않는 선결 분류 결과를 추가한다: 계약의 도급·위임·혼합 가능성, 약관성·개별교섭, 발주기관 유형, 적용 공공계약 체계. 불명확하면 후보와 필요한 사실을 남기고 법 적용을 단정하지 않는다.
2. 조항 유형 → 법률 분야 → 조문 후보의 조회 경로를 만든다. 제11조는 손해배상액 예정·진정한 위약벌·혼합 성격을 분리한다. 제14조는 계약 성질에 따른 해지 규정을 조사한다. 제19조는 기존 자산, 신규 산출물, 제3자·OSS, 권리 종류를 분해한다. 제22조는 계약상 지휘권과 실제 운용을 구별한다.
3. `RESEARCH_LIMITS.totalQueries=10`과 S3/S4 입력 예산을 함께 조정한다. 검색 상한에 걸린 쟁점은 근거 없는 결론으로 메우지 않고 조사 미완료로 표시한다.
4. 법률별 seed는 검색 후보일 뿐 결론 규칙이 아니다. 현행 조문·기준일 효력·판례 원문·사안 유사성을 기존 검증기로 확인한다. 샘플 README의 기대 항목은 탐지 회귀 기준이지 법리 정답이 아니다.

**완료 조건:** 제11·14·19·22·25조 및 지급조건마다 적용 후보 법체계와 그 전제가 보인다. 공식 근거가 없는 법적 효력 주장은 확정 표현으로 나오지 않는다.

### P3. 이중 검증, 공백, 수정안

1. `application.js`의 assessment에 `documentSupportIds`와 `authorityEvidenceIds`를 분리해 전달한다. 기존 `evidenceIds` 사용처는 단계적으로 이관한다. `verifyWarrants()`의 결합된 법률·사실 주장도 분리해 법적 명제는 공식 근거, 계약문언 명제는 D 원문과 검증한다.
2. D로 확인된 것은 “조항이 규정한다”까지만 뒷받침한다. “실제로 수행했다/손해가 발생했다/약관이다”는 별도 사실 근거가 없으면 추가 확인으로 둔다. 문언 주장과 D가 불일치하면 위험도와 수정안을 자동 확정하지 않고 게이트에 남긴다.
3. `counter`는 조항 해석 또는 법률상 실질 반론이고 관련 D·공식 근거가 있는 경우만 채택한다. 시스템 지침이나 단순 자료 부족 문구는 버린다. 검증되지 않은 counter만으로 외부 전문가 질의를 만들지 않는다.
4. S7은 결과를 바꿀 구체적 질문만 낸다. D가 이미 있는 경우 “D의 내용 확인” 또는 일반적인 “입증자료 확인” 질문을 금지한다.
5. HIGH/MEDIUM 문언 위험에는 효력 결론이 조건부여도 위험 완화용 수정안 후보를 만든다. 출처 확인에 실패한 조항은 수정안을 보류하고 이유를 남긴다. 누락조항 추가안은 기존 `redlineDiffs`와 구분한다.

**완료 조건:** D와 공식 근거의 검증 원장이 별도로 보이고, 제7·11·14·17·19·22조의 문언 위험 판단과 추가 사실 질문이 분리된다. 근거 없는 반대논리가 외부 질의로 올라가지 않는다.

### P4. 누락조항·보고서·호환성

1. 계약 유형과 사용자 질의에 맞는 `MissingClauseAudit`를 추가한다. 비밀유지 등 누락은 문서 전체와 부속서를 검사한 뒤 판정하고, 법적 필수·실무 권고·해당 없음·추가 사실 필요를 구별한다. 찾지 못했다는 이유만으로 법적 의무 위반이라고 쓰지 않는다.
2. 보고서와 화면의 쟁점 순서를 원문 → 문언 위험 → 적용 법체계/법률 검토 → 현재 효력 판단 → 결론을 바꿀 사실 → 수정 권고로 통일한다. `reasoningView.js`, `synthesis.js`, PDF/DOCX/HWPX/MD 내보내기, 이력 화면을 함께 갱신한다.
3. 저장된 `reasoning` 객체의 버전과 `PROMPT_VERSION`을 올린다. 이전 검토는 그대로 열 수 있어야 하며, 새 스키마와 다른 과거 결과를 조용히 재사용하지 않는다. 재검토 fingerprint와 외부 전문가 답변 연결도 확인한다.
4. 계약 경로의 전환은 feature flag로 시작한다. 기본 단일 호출 경로에도 같은 finding 모델을 적용하거나, 계약 프리셋에 한해 검증된 단계형 경로로 전환한다. 두 경로가 서로 다른 결론 형식을 내지 않도록 한다.

**완료 조건:** 샘플에서 비밀유지 조항 부재가 표시되고 제안 추가 문안이 별도 섹션에 나온다. 기존 비계약 프리셋, 저장 이력, 재검토 및 내보내기 형식이 깨지지 않는다.

## 3. 검증과 출시 기준

| 단계 | 검증 |
|---|---|
| 단위 | 원문 오프셋·표 셀·D 연결, fact provenance, 쟁점 병합, 법률/문서 warrant 분리, counter 차단, 누락조항 판정 |
| 파이프라인 | 샘플 계약의 제7·11·14·17·19·22·25조, 지급표, 비밀유지 부재를 모두 탐지. 제11조 두 금액을 별도 하위 쟁점으로 유지. 이미 등록된 D에 대한 부재 문구 0건. |
| 안전 | 모든 계약 쟁점에 D 또는 검증된 `MISSING_CLAUSE` 표지 연결. 법적 효력 주장에 공식·기준일 유효 근거 연결. 미검증 주장은 `HUMAN_REVIEW_REQUIRED` 유지. |
| 회귀 | `npm test`, 다른 4개 샘플, 재검토, 이력, 화면과 PDF/DOCX/HWPX/MD 출력. 구형 결과 읽기 시험. |
| 실측 | 같은 모델·설정으로 여러 번 실행해 `issueRecall`, `documentLinkRate`, 법령 근거 정확도·재현율, 누락조항 정확도·재현율, 수정안 커버리지, 모순율, 시간·토큰·실패율 기록. 전문가가 법리와 권고 문안을 표본 감수. |

샘플에서 `documentLinkRate=100%`, 존재하는 D의 허위 부재 진술 0건, 필수 9개 탐지 항목 9/9을 1차 통과 기준으로 둔다. 한 건의 샘플만으로 일반 성능을 확정하지 않는다. 긴 계약서, 표/부속서, 실제 개별교섭 자료, 조항이 없는 계약서, 다른 프리셋을 추가해 오탐과 비용을 확인한 뒤 기본 경로를 전환한다.

## 4. 우선 결정할 설계 사항

1. **식별자:** `DF7`처럼 조항 번호에 기대기보다 D ID와 원문 위치·해시를 기준으로 안정적인 출처 식별자를 정한다.
2. **처리 한도:** 8→15로 숫자만 올리지 않는다. 탐지는 보존하고, 조사 예산 초과 항목은 `UNREVIEWED`와 이유를 출력한다.
3. **위험도 의미:** HIGH는 문언상 협상·운영상 우선순위다. 무효 가능성의 확률이나 최종 법률 판단으로 표시하지 않는다.
4. **법리 검수:** 위약벌의 단순/혼합 성격, 약관성, 공공기관 적용 법제, IP 권리 종류는 판례·법령의 최신 원문 확인과 전문가 감수 후 seed를 확정한다.
