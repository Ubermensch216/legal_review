# 외부 전문가 질의 학습 루프 — 단계별 구축 계획

- 작성일: 2026-09-22
- 대상: `D:\Dev\legal_review` (HEAD `2c93355` + 미커밋 작업 트리)
- 근거 문서: `human_bridge_cure_review_report.md`(기획서), `docs/research/human-bridge-adoption-2026-09-22.md`(채택·반려 판단 근거)
- 코드상 명칭: **manual learning** (기획서의 "Human-Bridge CURE" / "Verified External Knowledge Loop")

---

## 1. 목표

소형(로컬) AI가 스스로 판단하지 못한 쟁점을 **비식별 질의서**로 만들고, 사용자가 대형 AI에서 받아온 답변을 **검증 가능한 지식 카드**로 바꿔 **같은 사건의 최종 검토에 되먹이는** 폐루프를 완성한다. 외부 AI API는 호출하지 않는다.

### 완성 후 사용자 흐름

```text
검토 실행
  → [탭 5] 외부 전문가 질의
     ① 로컬 AI가 미해결 질문 N개 추출 → 질의서 1건 생성
     ② 비식별 내역 확인 → 반출 준비 확인(READY)
     ③ 질의서 복사 → 대형 AI에 질의 → 답변 붙여넣기 (여러 번 가능)
        → 답변이 커버한 질문 자동 표시 (답변 3/4)
     ④ 지식 카드 검토 → 승인
     ⑤ 전 질문 충족 → [승인된 지식으로 최종 검토 다시 실행]
  → 최종 답변서 (사용한 지식·제외된 지식 사유 표시)
```

## 2. 핵심 설계 결정

| # | 결정 | 이유 |
|---|---|---|
| D1 | **질의서는 쟁점별로 쪼개지 않는다.** 질의서 1건 + 질문 N항목 | 쟁점마다 반출 승인을 반복시키면 형식적 승인이 된다. 조각내 여러 번 반출하면 조합 재식별 위험이 커진다. `preservedLogic`(유지해야 할 판단 조건)이 잘린다 |
| D2 | **답변은 여러 번 반입한다.** 답변 1건 → 카드 1장, 질문 다수 커버 | `importAnswer`가 이미 호출마다 카드를 만든다. 대형 AI는 질문 여러 개를 한 답변에 몰아 답한다 |
| D3 | **외부 답변 원문을 저장하지 않는다.** 구조화 카드 + 원문 해시만 | 원문에는 미검증 인용과 인젝션 문자열이 남는다. 개인정보 삭제 대상이 늘어난다. 기획서 §16 `RAW_EXTERNAL`은 반려 |
| D4 | **신규 테이블을 만들지 않는다.** `manual_learning` 단일 테이블 유지 | `kind`+`parent_id`+`revision`으로 기획서 §19의 두 테이블을 이미 표현한다. 늘리면 개인정보 삭제 경로가 갈라진다 |
| D5 | **원문 대비 diff를 보여주지 않는다.** 치환 토큰 하이라이트 + 건수 | 반출 화면에서 비식별 이전 원문을 다시 내려보내는 것은 기능 목적에 반한다 |
| D6 | **긴 답변은 컨텍스트를 키우기보다 쪼갠다** | 2B급 모델에 12k 토큰 한국어 법률문을 한 번에 물리는 것보다 2k씩 나눠 물리는 쪽이 누락이 적다. 호출 증가는 품질 대가를 지불하고 사는 것 |
| D7 | **구조화 JSON 직접 반입은 사용자가 명시적으로 고른다.** 자동 감지 금지 | 붙여넣은 내용이 시스템 동작을 바꾸면 그 자체가 인젝션 표면이 된다 |
| D8 | **지식이 제외된 사유는 반드시 화면에 표시한다** | 조용한 제외는 "답변을 다 넣었는데 반영이 안 됐다"로만 보인다. 기능이 아니라 신뢰성 표시다 |

### F1 정정 — 운영 `.env`가 이미 예산을 올려두었다

최초 진단은 라이브러리 기본값(`contextTokens` 16,384 / 한글 1.9 토큰·자)으로 계산한 것이다.
그러나 이 PC의 `.env`에는 모델별 프로파일이 이미 설정되어 있다.

```text
LLM_MODEL_BUDGETS={"ollama:gemma4:e2b":{"contextTokens":40960,"outputTokens":8192,"tokensPerChar":{"hangul":0.75}}}
```

두 설정에서 실제로 넣을 수 있는 한국어 입력량(측정값):

| 설정 | 출력 예약 | `inputLimit` | 한국어 입력 상한 |
|---|---|---|---|
| 라이브러리 기본 | 8,192 | 7,680 | 약 3,400자 |
| 라이브러리 기본 + 작업별 예산(card) | 5,120 | 10,752 | 약 4,800자 |
| **이 PC 운영 설정** | 8,192 | 32,256 | **약 37,000자** |
| 이 PC 운영 설정 + 작업별 예산(card) | 5,120 | 35,328 | 약 40,600자 |

**즉 이 PC에서는 24,000자 답변이 이미 예산 안에 들어간다. "사실상 모든 답변이 413"이라는 진단은 이 배포에는 해당하지 않는다.**
기본 설정으로 배포되는 다른 PC에서는 여전히 성립하므로 Phase 1의 예산 분리는 유지한다.

### 실제 토크나이저 계수 측정 (2026-09-22, 로컬 Ollama `gemma4:e2b`)

프로파일의 `hangul: 0.75`가 실제보다 작으면 추정은 통과하지만 Ollama가 `num_ctx`를 넘는
프롬프트 앞부분을 조용히 잘라내므로, 실제 모델로 `prompt_eval_count`를 측정해 확인했다.

| 텍스트 | 실측 한계 계수 | 시스템 추정 / 실제 |
|---|---|---|
| 단순 한국어 법률문 (1,480 ~ 22,200자) | 0.568 토큰/자 | — |
| 조문·판례·표·숫자·영문이 섞인 답변 형태 (902 ~ 13,530자) | 0.632 토큰/자 | **2.01배** |

**결론: 프로파일은 과소가 아니라 약 2배 과대 추정이다. 조용한 잘림 위험은 없다.**
방향이 안전한 쪽(예산을 실제보다 빨리 소진했다고 판단)이므로 프로파일은 그대로 둔다.
계수를 실측값으로 낮추는 것은 잘못 잡으면 위험한 방향이라 권하지 않는다. 대신 Phase 1에서
넣은 런타임 보정이 첫 호출 이후 자동으로 실제에 맞춘다(아래 실측 확인).

참고로 24,000자 한국어 답변의 실제 토큰은 약 13,600~15,200 토큰으로, 이 PC의 `num_ctx`
40,960에 충분히 들어간다.

### Phase 1. 로컬 예산 분리 — ✅ 완료 (2026-09-22)

**목적**: 코드 2~3곳 변경으로 "사실상 모든 답변이 413" 상태를 푼다.

**변경**

1. `manualLearningLocal.js` — `callLearningLocal(system, user, { outputTokens })` 로 작업별 출력 예산을 받는다. 현재는 `resolveBudget('ollama', { model })`만 호출해 출력에 8,192 토큰을 예약한다. 산출물은 JSON 카드 한 장이므로 과하다.

   | 작업 | `outputTokens` | 결과 `inputLimit` |
   |---|---|---|
   | 쟁점 분석 (`createInquiry`) | 2,048 | 13,824 |
   | 청크 추출 (Phase 5) | 1,024 | 14,848 |
   | 카드 생성 (`importAnswer`) | 4,096 | 11,776 |

   `resolveBudget`은 이미 `config.outputTokens` 덮어쓰기를 지원한다. 검토 본 경로의 예산은 건드리지 않는다.

2. `manualLearning.js:100` — 답변 길이 상한을 **예산에서 역산해 검사**한다. 고정 24,000자를 남겨두되(DoS 방어), 그 전에 `createTokenCounter('ollama', {model}).estimate(system, user)`로 재보고 초과 시 **413이 아니라 "답변이 길어 나누어 처리합니다"** 경로(Phase 5)로 보낸다. Phase 5 이전에는 초과 문자수를 알려주는 400으로 돌린다: `"답변이 약 N자 초과입니다. 핵심 부분만 붙여넣거나 OLLAMA_NUM_CTX를 늘리십시오."`

3. `manualLearningLocal.js` — **모델이 보고한 실제 입력 토큰(`prompt_eval_count`)과 대조한다.**
   추정 계수가 실제보다 작으면 Ollama가 프롬프트 앞부분을 조용히 잘라내고, 잘린 입력으로도
   JSON은 정상 출력되어 파싱만으로는 알 수 없다. 실제 토큰이 한도를 넘으면 결과를 버리고
   413으로 알리며, 관측값을 `recordObservation`에 넣어 다음 추정을 보정한다.

4. `manualLearningLocal.js` — **출력이 잘린 경우와 응답이 깨진 경우의 오류를 분리한다.**
   전자는 `OLLAMA_NUM_PREDICT`를, 후자는 Ollama 상태를 봐야 하므로 조치가 다르다.
   메시지에는 토큰 수만 넣고 모델 원문은 올리지 않는다.

**수용 기준**: 예산 초과 시 **얼마나 초과했는지**가 오류에 담긴다. 실제 입력이 예산을 넘으면 결과를 저장하지 않는다.

**결과**: 작업별 출력 예산으로 `inputLimit`이 7,680 → 10,752(카드) / 12,800(분석) 토큰으로 늘었고,
같은 시스템 프롬프트 기준 한국어 입력 상한이 약 3,400자 → 4,800자 / 5,700자가 되었다.
운영자가 `OLLAMA_NUM_PREDICT`를 더 작게 잡은 경우에는 그 설정을 넘지 않는다.
`createInquiry`의 45,000자 고정 상한도 예산 역산 검사로 교체했다(같은 결함이 분석 호출에도 있었다).

**테스트**: T3(실제 토큰 초과 시 폐기, 잘림/깨짐 오류 구분), T6(예산 초과 안내, 작업별 예산 속성) 4건 추가.

**실제 모델 확인** (로컬 `gemma4:e2b`): `callLearningLocal`이 스트리밍 경로로 정상 JSON을
반환했고, `prompt_eval_count` 기반 보정이 동작해 같은 프롬프트의 추정이 한 번의 호출 뒤
132 → 92 토큰(-30%, 보정비 0.698)으로 실제에 수렴했다. 보정은 프로세스 수명 동안만
유지되므로 서버를 재시작하면 다시 보수적 추정에서 시작한다(설계상 의도).

### Phase 2. 질문 항목화와 커버리지 — ✅ 완료 (2026-09-22)

**목적**: "답변 3/4" 를 가능하게 하는 데이터 모델 변경. 백엔드 전용.

**변경**

1. `manualLearning.js:49` `createInquiry` — 로컬 AI가 낸 `questions`를 마크다운 본문에만 넣지 말고 `store.create`의 데이터에 `questions: [{ id, text }]`로 **함께 저장**한다. 본문 렌더링은 이 배열에서 생성해 번호를 일치시킨다.

2. `manualLearning.js:98` `importAnswer` — 로컬 AI 출력 스키마에 `answeredQuestions: [질문 번호]`를 추가한다. 카드 데이터에 `answeredQuestions`, `answerHash`(원문 해시, D3), `providerLabel`(사용자 입력 자유문자열, 신뢰도에 미반영)을 저장한다.

3. 조회 응답에 **커버리지 요약**을 포함한다: 질문별 `{ 미답변 | 답변됨(카드 id) | 승인됨 }`.

**주의**: 추출 단계 프롬프트에는 **질의서 전문이 아니라 번호 붙은 질문 목록만** 넣는다. 전문을 함께 보내면 Phase 5에서 청크마다 그 비용을 반복 지불하게 된다.

**수용 기준**: 답변 1건을 반입하면 그 답변이 커버한 질문만 상태가 바뀐다. 두 번째 답변 반입 시 나머지가 채워진다.

**테스트**: T7 — 답변 2건으로 질문 4개가 모두 충족되면 커버리지가 4/4가 된다. 범위 밖 번호를 내면 무시한다.

**설계 변경**: 질문 목록을 별도 저장하지 않고 **질의서 본문에서 파생**한다(`parseInquiryQuestions`).
사용자가 본문을 편집할 수 있으므로 별도 목록을 원본으로 삼으면 실제로 외부에 나간 질문과
진행 상태가 어긋난다. 편집으로 질문 항목을 통째로 지우면 400으로 막는다.

**추가 구현**: 같은 답변의 중복 반입 차단(`answerHash`), 답변 출처 라벨(`providerLabel`,
표시 전용이며 신뢰도에 미반영), 어느 질문에도 연결되지 않은 카드 노출(`coverage.unassigned`),

**실제 모델 확인** (`gemma4:e2b`, 질의서 생성 → 답변 반입 → 커버리지 전 구간): 파이프라인은

### Phase 4. 폐루프 — ✅ 완료 (2026-09-22)

**목적**: 승인된 지식이 **같은 사건의 최종 검토**에 반영되게 한다.

**변경**

- `sourceHistoryId`는 실제 이력이 있을 때만 받는다(없으면 404). 남의 사건 지식을 끌어오지 못한다.

**UI**: STEP 5에서 미충족 질문 번호를 알리고(부분 충족 실행 허용), 직전 검토에 실린 지식과
적용하지 않은 지식을 사유와 함께 보여준다. 최종 검토는 별도 실행 경로를 만들지 않고 기존
검토 폼을 채워 그대로 제출한다 — 공식 근거를 다시 수집해야 하고, 그 결과가 승인 지식의
적용 범위와 맞는지 다시 따져야 하기 때문이다.

**첨부문서 제약**: 이력에는 문서 원문이 아니라 발췌만 남는다. 원 검토에 첨부가 있었다면
재검토 시 다시 첨부해야 같은 조건이 되며, UI가 이를 확인 대화로 알린다.

**추가로 고친 것**: 서버 목록에서 동기화된 이력은 IndexedDB에 **요약만** 저장되어 복원 시
검토 본문이 비어 있었다(기존 결함). 복원 시 본문이 없으면 `GET /history/:id`로 보충한다.

**미완 검증**: 브라우저에서 재검토 실행(POST 전송·폼 자동 채움·STEP 5 표시)까지는 확인했으나,
로컬 `gemma4:e2b`의 검토 생성이 15분 이상 걸려 **최종 결과 화면에 사용/제외 지식이 표시되는 것은
눈으로 확인하지 못했다.** 해당 경로는 T9로 검증되어 있다.

### Phase 5. 긴 답변 처리 — ✅ 완료 (2026-09-22)

**목적**: Phase 1로도 넘치는 답변(1만 자 이상)을 처리한다.

#### 5-A. 구조화 JSON 직접 반입 (먼저, 싸다)

질의서는 이미 대형 AI에게 마지막에 카드 JSON으로 정리해 달라고 요청한다(`CARD_SCHEMA`). 대형 AI가 응하면 붙여넣을 것은 JSON 블록 하나이고 **로컬 AI 호출이 0회**다. 경로는 `validateKnowledgeCard` → `redactLearningText` → `checkLearningCitations`.

**사용자가 UI에서 명시적으로 고르는 경로여야 한다**(D7). 붙여넣은 내용에 JSON이 보인다고 자동으로 빠른 경로를 타면, 외부 답변의 내용이 시스템 동작을 바꾸는 셈이다.

#### 5-B. map-reduce 청킹

```text
비식별(전체 1회) → 청킹 → [추출 × N] → 통합 → 카드
```

| 규칙 | 내용 |
|---|---|
| R1 | **비식별은 청킹 전에 전체 텍스트에 한 번만.** `redactLearningText`는 호출 단위로 `[성명_1]`, `[성명_2]` 번호를 매긴다. 청크별로 돌리면 같은 사람이 청크마다 다른 번호가 되어 동일인 판단이 깨진다 |
| R2 | **청크 크기는 상수로 박지 않는다.** `createTokenCounter(...).estimate()`로 `inputLimit`의 70% 선까지 실측으로 채운다. "3,000자"로 박으면 `OLLAMA_NUM_CTX`나 모델 변경 시 깨진다 |
| R3 | **주장과 근거가 갈라지는 경계에서 자르지 않는다.** 제목·빈 줄 경계로 자르고 1~2문장 겹친다. 한국어 법률 답변은 "…할 수 있다. 근거: 공유재산법 제20조" 형태라 고정 글자수로 자르면 근거만 떨어진 청크가 생긴다 |
| R4 | **주장 없는 인용은 버린다.** 근거만 있는 청크의 인용을 그대로 올리면, 존재 검증만 통과해 "검증됨"처럼 보인다. 누락보다 나쁘다 |
| R5 | **추출 단계에 질의서 전문을 넣지 않는다.** 번호 붙은 질문 목록만 넣는다(Phase 2). 통합 단계에서만 전문을 쓴다 |
| R6 | **통합 단계는 병합·중복제거만 한다.** 새 주장 추가 금지. 인용은 청크에서 온 문자열 그대로 통과시키고, 이후 `checkLearningCitations`로 다시 검증한다 |
| R7 | **부분 실패를 완성된 카드로 내지 않는다.** 카드에 `chunkCoverage: {total, processed}`를 남기고, 미완이면 `approveKnowledge`를 막는다. 답변의 40%로 만들어진 지식이 완전한 얼굴로 저장되어 이후 검토에 재사용되는 것이 이 설계의 최악 실패 모드다 |
| R8 | **시간 예산.** `callLearningLocal`의 타임아웃은 호출당 180초다. 12청크면 최악 36분 동안 HTTP 요청이 물린다. 청크 수 상한(12) + 전체 마감시간 + 진행 표시(SSE) 또는 비동기 잡 중 하나는 함께 간다 |

**수용 기준**: 15,000자 답변이 카드 1장으로 정리되고, 인용이 주장과 함께 보존되며, 중간 실패 시 카드가 미완으로 표시되어 승인이 막힌다.

**테스트**: T11 — 청크 경계에 걸친 "주장+근거"가 보존된다. T12 — 청크 3개 중 2번이 실패하면 카드가 `chunkCoverage` 미완으로 표시되고 승인이 409로 막힌다. T13 — 비식별 토큰 번호가 청크 전체에서 일관된다.

## 8. 남은 판단 사항

- **90일 실효 기간**: 사건 내 루프에는 무관하나 장기 보관 지식의 기본값으로 적절한지는 운영 판단.
- **다중 사용자**: 현재 승인 시각은 남지만 "누가"는 남지 않는다. 기관 배포 전에 정해야 한다.
- **`OLLAMA_NUM_CTX` 상향 여부**: Phase 1의 예산 분리로 부족하면 검토. 다만 소형 모델의 장문 이해도 문제는 컨텍스트 확대로 해결되지 않는다(D6).

**결과 (Phase 6)**

- **판례·해석례 번호 검증** (`checkLearningCases`): 카드 스키마의 `citations`에는 조문만 들어가므로,
  산문 속에 끼워 넣은 사건번호(`2018두42955`, `2019헌가12`)는 지금까지 **아무 검증도 받지 않고
  '확인된 근거'처럼 읽혔다.** 이제 본문에서 뽑아 이번 검토가 확보한 공식 판례·해석례와 대조한다.
  목업 자료는 근거로 치지 않는다.
- **재사용 차단**: 확인되지 않은 사건번호가 하나라도 있으면 제외 사유 `CASE_UNVERIFIED`로
  재사용에서 빠진다. 조문만 맞고 판례가 지어낸 것이면 그 지식은 근거 없는 법리를 실어 나른다.
- **시행 여부 구분**: 수집은 했으나 검토 기준일에 시행 중이 아닌 조문은 `OUT_OF_FORCE`로
  표시한다. 종전에는 존재하지 않는 조문과 똑같이 `UNVERIFIED`로 뭉뚱그려졌다.

**테스트**: T11 3건(사건번호 존재·목업 배제·헌재 번호, 시행 여부 구분, 미확인 사건번호의 재사용 차단).

**실제 확인**: 지어낸 `2099두99999`를 담은 카드를 반입해 조문은 `VERIFIED_EXISTENCE`,
사건번호는 `UNVERIFIED`로 갈라지는 것과, 화면에 "확보한 자료에서 확인 불가 — 이 지식은
재사용되지 않습니다"로 표시되는 것을 확인했다.

**하지 않은 것**: 카드별 사용 횟수·실패 이력 집계와 그에 따른 재사용 우선순위. 검토 저장 경로에
쓰기를 추가해야 해서 이번 범위에서 제외했다. 현재 우선순위는 사건 내 지식 → 쟁점어 일치 수 순이다.
